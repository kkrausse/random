# BOOX Kindle Context POC Progress

Generated: 2026-08-01 09:57:50 PDT

## Goal

Build a proof-of-concept Android app for a BOOX Palma 2 that can collect context from the Kindle app, eventually send that context and a question to a server, and display an AI-generated response.

The first objective was to determine what data a normal, non-rooted Android app can obtain from Kindle. The project intentionally avoids the BOOX SDK because no BOOX-specific stylus, editor, or rendering integration is currently needed.

## Current Result

The screenshot path works.

The app runs an Android accessibility service that displays a black `ASK` overlay. Pressing `ASK` while Kindle is visible captures the current screen, stores it privately as a PNG, opens the POC activity, and displays a scaled preview.

Confirmed capture properties:

- Resolution: 824 x 1648
- Format: PNG, 8-bit RGBA
- Observed file size: approximately 186 KB (189,992 bytes)
- Private device path: the app's internal `files/kindle-page.png`
- Network behavior: none
- OCR behavior: none
- Server behavior: none

Direct extraction of the book prose through Android accessibility does not work in the tested Kindle build. Kindle exposes its controls but not the rendered page text.

## Implemented Features

### Accessibility Service

`KindleAccessibilityService` currently:

- Retrieves accessibility window content.
- Receives window state, window content, and view scroll events.
- Creates a `TYPE_ACCESSIBILITY_OVERLAY` button labeled `ASK`.
- Keeps the ASK button visible because BOOX NaviBall generates unrelated accessibility events that made package-based visibility unreliable.
- Traverses the active accessibility tree and stores any available text and content descriptions.
- Uses `AccessibilityService.takeScreenshot()` when ASK is pressed.
- Writes the latest screenshot to private app storage as `kindle-page.png`.
- Opens the main POC activity after capture succeeds or fails.
- Reports an Android screenshot error code if capture is blocked.

The service requests the following capabilities through `accessibility_service_config.xml`:

- `canRetrieveWindowContent=true`
- `canTakeScreenshot=true`
- `flagReportViewIds`
- `flagIncludeNotImportantViews`
- `flagRetrieveInteractiveWindows`

### Main Activity

`MainActivity` currently:

- Opens Android accessibility settings.
- Opens Kindle.
- Displays the latest accessibility text or diagnostic.
- Displays the latest screenshot as a scaled preview.
- Registers an Android `ACTION_PROCESS_TEXT` handler named `Ask with Context`.
- Registers an Android `ACTION_SEND` text share target named `Send to Kindle Context`.
- Stores received selected/shared text in private preferences.

Android 11+ package visibility initially caused `getLaunchIntentForPackage("com.amazon.kindle")` to return null. This was fixed by adding a `<queries>` entry for `com.amazon.kindle` to the manifest.

### Privacy Defaults

- The app declares no `INTERNET` permission.
- Screenshots remain in private internal app storage.
- Shared preferences and screenshots are excluded from cloud backup and device transfer.
- Each screenshot replaces the previous screenshot instead of accumulating an unbounded history.
- There is currently no analytics, remote logging, OCR, AI request, or server upload.

## Experiments And Findings

### 1. Android Accessibility Hierarchy

The initial test used Android's UI Automator directly, without an APK:

```bash
adb shell uiautomator dump /sdcard/kindle-window.xml
adb pull /sdcard/kindle-window.xml .
```

A complete hierarchy dump was taken while the foreground activity was Kindle's standalone book reader. The only non-empty accessible string was:

```text
content-desc="Add bookmark"
```

The custom accessibility service produced the same result. It could read `Add bookmark`, proving that the service and tree traversal worked, but it could not read the page prose.

Conclusion: this Kindle build renders the book page without exposing its prose as Android accessibility text. A normal app cannot obtain the visible page text from the accessibility node tree.

### 2. Kindle Private Data

A normal Android app cannot read Kindle's private databases, files, reading history, or DRM-protected book content because Android application sandboxing prevents access to another app's private storage.

Rooting was not attempted and is not part of the current design.

Conclusion: previously read context cannot be recovered directly from Kindle's private storage. The app must prospectively collect context from user-triggered screenshots or text that Kindle explicitly shares.

### 3. Android Text Actions

The app registered an `ACTION_PROCESS_TEXT` activity so it can appear in Android's standard text-selection menu as `Ask with Context`.

This action appears in the BOOX default reading app, confirming that the registration is valid. It does not appear in Kindle.

Conclusion: Kindle uses a custom selection toolbar instead of Android's standard process-text action mode. Another normal app cannot inject a custom action into Kindle's private toolbar.

The process-text integration remains useful for BOOX's reader and other apps that use standard Android text actions.

### 4. Android Share Target

The app also registered an `ACTION_SEND` handler for `text/plain`, exposed as `Send to Kindle Context`.

The target was not available through the tested Kindle selection flow.

Conclusion: Kindle's custom toolbar did not provide a usable selected-text share path in this test. The handler remains implemented because it may work in other readers or other Kindle screens.

### 5. On-Device OCR

An intermediate build added bundled Google ML Kit OCR, but this direction was rejected before device testing because the Palma 2 is resource-constrained and the eventual architecture already requires a server/AI request.

ML Kit and all of its dependencies were removed. The current APK performs no OCR.

Conclusion: if OCR is needed, perform it on the server or use a server-side multimodal model. Do not spend Palma CPU, memory, battery, or storage on local OCR unless offline support becomes a requirement.

### 6. Accessibility Screenshot

The app was changed to request accessibility screenshot capability and save the captured bitmap as PNG.

The final device test succeeded. The screenshot displayed correctly in the POC activity and contained the Kindle page.

Conclusion: Kindle does not block accessibility screenshots on this Palma 2 configuration. This is the viable path for collecting visible Kindle context.

### 7. BOOX NaviBall Versus ASK

BOOX NaviBall is a separate accessibility service and creates its own bottom-right tab. That tab was initially mistaken for the POC control.

The POC's control is a black button labeled `ASK`, positioned at the middle-right edge. It is implemented as an accessibility overlay.

NaviBall also generates accessibility events after Kindle events. Hiding ASK on every non-Kindle event made ASK disappear even while Kindle remained foreground. The current POC keeps ASK visible to avoid this BOOX-specific event noise.

Future versions should determine the true foreground package from the active/root window and ignore overlay-service events rather than leaving ASK globally visible.

### 8. Accessibility Service State

Reinstalling/updating the APK sometimes left the service listed as crashed or disabled until it was enabled again. Adding an accessibility shortcut was not equivalent to enabling the service.

The confirmed healthy state contains both services:

```text
Bound services:
- NaviBall
- Kindle Context Capture

Enabled services:
- com.onyx.floatingbutton/.service.FloatButtonAccessibilityService
- dev.example.kindlecontext/dev.example.kindlecontext.KindleAccessibilityService

Crashed services: none
```

The user-facing path is to enable `Kindle Context Capture` in Android accessibility settings.

For this connected development device, the service was also enabled through ADB while preserving NaviBall:

```bash
adb shell settings put secure enabled_accessibility_services \
  'com.onyx.floatingbutton/.service.FloatButtonAccessibilityService:dev.example.kindlecontext/dev.example.kindlecontext.KindleAccessibilityService'
adb shell settings put secure accessibility_enabled 1
```

This ADB method is for development only. A production app must send the user to accessibility settings and cannot silently grant itself accessibility access.

## Current User Flow

1. Install the debug APK.
2. Open `Kindle Context POC`.
3. Tap `Enable accessibility service` if `Kindle Context Capture` is not enabled.
4. Tap `Open Kindle`.
5. Navigate to a book page.
6. Press the black `ASK` button at mid-right.
7. Wait while the button says `WAIT`.
8. The POC opens and displays the captured page under `SCREENSHOT PREVIEW`.
9. The app also displays the accessibility text, currently expected to contain only `Add bookmark` for Kindle pages.

## Recommended Next Architecture

The proven next-stage flow is:

```text
User presses ASK
  -> accessibility service captures current Kindle page
  -> app opens a compact question UI
  -> app sends screenshot plus question to an authenticated HTTPS endpoint
  -> server performs OCR or sends the image directly to a vision-capable model
  -> server combines current page with previously captured session context
  -> server returns a concise answer
  -> app displays the answer in an overlay or lightweight activity
```

Recommended server-side responsibilities:

- Authentication and request authorization
- Image size validation
- OCR or multimodal extraction
- Context deduplication between consecutive pages
- Session-scoped context storage
- AI provider credentials
- Prompt construction
- Retention and deletion policy
- Rate limiting and cost controls

Recommended device-side responsibilities:

- Explicit user-triggered capture
- Preview and confirmation before upload, at least during development
- Question input
- Image scaling/compression before upload
- Clear capture/upload status
- Response display
- A local clear/delete action
- A service toggle or Kindle-only overlay visibility
- No embedded AI provider secret

## Bottom Line

The original preferred path, direct Kindle text extraction, is not available because Kindle exposes only UI controls such as `Add bookmark` through Android accessibility. Standard text actions work in BOOX's reader but Kindle uses a custom selection toolbar. Kindle also did not expose a useful share-target path in the tested flow.

The important feasibility result is positive: an accessibility service can capture the visible Kindle page as a normal screenshot on the non-rooted BOOX Palma 2. That provides enough input for a server-side OCR or multimodal AI pipeline without burdening the Palma with local OCR.

## Follow-Up Experiment: Spoken Accessibility And Page History

Tested later on 2026-08-01 with Kindle 8.148.1.0 and the connected Palma 2.

The earlier direct-text conclusion was incomplete. Kindle changes its accessibility behavior based on the service's declared feedback type. Changing the POC service from `feedbackGeneric` to `feedbackSpoken` caused Kindle to expose virtual book-content nodes. The accessibility tree then contained raw prose from the current page and surrounding content, in addition to `Add bookmark`. Touch exploration was not requested or enabled.

Observed page-turn behavior:

- A normal horizontal page swipe successfully changed the visible page.
- Kindle emitted no accessibility event for that page turn, even with `typeAllMask` configured.
- Event-triggered screenshot capture is therefore not reliable for page history.
- Polling `AccessibilityService.takeScreenshot()` while Kindle is foreground successfully detected the changed page.
- A 64-bit visual hash discarded repeated captures of an unchanged page.
- The app now retains `kindle-page-current.png` and `kindle-page-previous.png` instead of accumulating an unbounded history.

The custom `ASK` accessibility overlay was removed. The service now requests Android's accessibility button and handles its callback. On this BOOX device that is the floating `K` shortcut. Pressing `K` captures the current state and opens the POC activity, which previews both retained pages.

Important qualifications:

- Declaring `feedbackSpoken` changes some Kindle interaction behavior and exposes accessibility focus in page-overview mode. This needs more usability testing before treating it as the final configuration.
- Polling currently runs every 1.5 seconds only while Kindle is the active accessibility window.
- Kindle reader menus or page-overview screens could enter the visual history because they use the same package and reader activity; page-content classification remains future work.
- The raw accessibility prose is now preferable to OCR for text context when available. Screenshots remain useful for illustrations, layout, unsupported book formats, and fallback behavior.

### Text-First Revision

After confirming the raw prose path, automatic screenshot capture was disabled and the screenshot preview UI was removed. The POC now polls the Kindle accessibility hierarchy every 1.5 seconds while Kindle is foreground, retains the latest two distinct prose snapshots, and ignores short reader-control hierarchies that do not resemble book prose. The `K` shortcut now opens the captured text without taking a screenshot.

The text-only build captured 3,154 characters of raw prose from 37 accessibility nodes while the book was in its normal full-page reading view. Existing screenshot files from the earlier experiment remain in private app storage but are no longer read, displayed, or updated.

### Highlighted Text Experiment

The K shortcut now checks every Kindle accessibility node for standard Android text-selection offsets before opening the POC. When Kindle exposes valid offsets, the app displays only those substrings under `HIGHLIGHTED TEXT` while retaining the broader current and previous contexts below. If Kindle's custom highlight implementation does not publish selection offsets, the app reports that no highlighted text was exposed; this must be verified on the Palma because support is controlled by Kindle's virtual accessibility nodes.
