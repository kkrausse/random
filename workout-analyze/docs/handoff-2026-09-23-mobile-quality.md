## Segment-quality investigation

- The **mobile worker imports the same** `src/services/SegmentDetector.ts` as the original web pipeline; `mobile/src/analysis/worker.ts` invokes `detectRoutes`, and `src/engine/analysis.ts` reads normalized workouts and publishes derived tables. Thus “mobile analysis is worse” is a real user observation, but do not assume there are two different algorithms. Compare inputs, config, persistence, navigation, map styling, filtering, and presentation before tuning detection.
- Original web analysis UX: `src/components/AnalysisRouteList.tsx` has type/sport/min-workout filters, ranked cards, match/traversal/workout stats; `src/components/AnalysisSettings.tsx` exposes detector parameters; `src/components/RouteDetailShared.tsx`, `LoopRouteDetail.tsx`, `SegmentRouteDetail.tsx`, and `WorkoutDetail.tsx` have richer effort/history/comparison views. Mobile is condensed into `mobile/src/App.tsx` (`Routes`, `RouteDetailScreen`, `LibraryDetail`, `SavedDetail`) and `mobile/src/styles.css`; it lacks several controls and may hide why a route was or was not matched.
- Reproduce with representative known rides in both apps. Compare canonical `activities`/`activity_samples` counts and source/version, analysis config in `analysis_settings`, route IDs/counts, `route_traversals`, scores, route geometry, and effort selection. If the same inputs/config produce divergent output, write a focused regression fixture and find where SQL/serialization/worker/native host differs. If output matches, fix ranking/filtering/visualization and identify genuinely poor matches from the detector with examples; do not just increase route counts or claim zero iPhone matches is expected quality.
- Native migration/import is a prerequisite to phone analysis comparisons. `Workout library → Import from Mac`, then `Import saved iPhone workouts`; `Segments & loops → Run/Rebuild segment analysis`. These are separate actions. Validate each result and avoid reimporting/mutating the durable recorder archive.
