## VPN and isolation assessment

The live `inet palma_guard` table was inspected. It denies AP forwarding to
private, link-local, shared-address, and multicast/reserved IPv4 ranges; denies
non-Ethernet egress and IPv6; and restricts Pi input to DHCP/DNS. Current LAN
and Docker routes fall within the denied ranges. Counters include historical
drops but cannot date or attribute individual attempts to this reconnect. [^pi]

Current traffic is consistent with the policy **freshly verified over USB at
08:26**: Tailscale always-on, lockdown enabled, reader/Gmail/1Password UID
inclusion, Chrome/Kindle exclusion, and no exit-node default route. Prior user
tests found Chrome and Kindle offline; those are historical tests. [^policy]
[^history]

**App restrictions are not full-tunnel privacy.** Without an exit node, direct
public traffic is expected and is not automatically a VPN bypass. The system
also previously made Android validation probes under lockdown. Current Google
validation-like traffic and local Kindle-related DNS show why the policy must
not be described as blocking every excluded-app-related or system packet.
Encrypted Tailscale contents are not visible in the gateway capture. [^policy]
[^probes] [^first-window] [^exit-node]

The Pi guard controls the outer network path. An authorized connection carried
inside an encrypted Tailscale relay can still reach a permitted tailnet peer;
AP isolation does not override tailnet permissions or inspect inner traffic.
This is an architectural limitation, also consistent with the established
reader tailnet socket. [^sockets] [^exit-node]

### Local-network activity: fuller historical review

The baseline contained **12 mDNS queries: six IPv4 and six IPv6**, for
`_meshcop._udp.local`, a Thread border-router discovery service, as well as
normal IPv6 setup traffic. The initial report counted only the six IPv6 queries;
the frame-level recheck also identified the six IPv4 multicast counterparts.
This is actual local service discovery. It is not a broad address/port scan,
and no returned device inventory or subsequent inventory upload was established.
Other baseline local IPv4 traffic was directed to the AP gateway or DHCP
broadcast, primarily DNS and unsuccessful DNS-over-TLS attempts. [^discovery]

The later ring contains repeated UDP/41641 attempts to the Pi's AP, LAN, and
container addresses. Those destinations match the Pi's interface inventory
and Tailscale's usual peer-connectivity port, consistent with advertised peer
candidate testing. It also contains DNS-over-TLS attempts to private/shared
resolver addresses. These are attempts visible before forwarding decisions,
not proof of successful LAN access. The live guard denies these paths; this
review did not perform a simultaneous uplink capture or an end-to-end physical
client isolation test. No broader port/address-scanning pattern was found in
the extracted metadata. Passive listening cannot be ruled in or out. [^ring]
