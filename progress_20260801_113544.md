# Kindle Context POC Progress

Updated: 2026-08-01 11:35 PDT

## Current State

The text-first accessibility POC is installed on the BOOX Palma 2 and works when BOOX is configured not to freeze it. Kindle exposes raw prose to the service because the service declares `feedbackSpoken`. Pressing the floating K accessibility button captures the current tree and switches to the POC activity.

The app now has a `HIGHLIGHTED TEXT` section above the broader current and previous text contexts. It checks every Kindle accessibility node for standard Android selection offsets. If no offsets are available, it explicitly displays:

> No highlighted text was exposed by Kindle. The full text context is still available below.

The debug APK builds successfully at:

```text
app/build/outputs/apk/debug/app-debug.apk
```

## Critical BOOX Setup

BOOX Freeze Settings must be disabled for `Kindle Context POC`. This was the cause of the disappearing K button and failed app switching during this experiment.

When freezing was enabled, BOOX did all of the following as soon as the POC went into the background:

- Disabled the entire package with package state `enabled=3`.
- Killed the accessibility-service process.
- Removed the service from `enabled_accessibility_services`.
- Cleared the accessibility-button target.
- Reported `KindleAccessibilityService` under crashed services.
- Left only the separate BOOX NaviBall service active.

Normal Android background app-ops and the device-idle whitelist did not override BOOX freezing. The decisive fix was made on the device:

1. Open BOOX Settings.
2. Open `Apps & Notifications`.
3. Open `Freeze Settings` / `App Freeze`.
4. Find `Kindle Context POC`.
5. Turn freezing off for the app.

The same screen has `Automatically enable freezing after installing an app`. If that remains enabled, check the POC's freeze state after every APK install or update. It may be preferable to disable automatic freezing during development.

For long-term reliability, also configure the app to stay active in the background through BOOX app optimization and enable autostart if this firmware offers those controls. Those settings were not the direct cause observed in this run, but they are appropriate for a persistent accessibility service.

After an install or a freeze event, verify these items:

1. The package is not frozen or disabled.
2. `Kindle Context Capture` is enabled in Android accessibility settings.
3. The floating K accessibility button targets `Kindle Context Capture`.
4. BOOX NaviBall remains enabled or disabled according to user preference; it is a separate service.
5. Pressing K in Kindle opens `Kindle Context POC`.

Development-only ADB recovery commands used in this session were:

```sh
adb shell pm enable dev.example.kindlecontext
adb shell settings put secure enabled_accessibility_services \
  'com.onyx.floatingbutton/.service.FloatButtonAccessibilityService:dev.example.kindlecontext/dev.example.kindlecontext.KindleAccessibilityService'
adb shell settings put secure accessibility_button_targets \
  'dev.example.kindlecontext/dev.example.kindlecontext.KindleAccessibilityService'
```

If Android retains a stale crashed-service state, toggle only `Kindle Context Capture` off and back on in accessibility settings. Do not disable NaviBall unless that is intentional.

## Highlight Experiment

A successful diagnostic capture was made at approximately 11:33 PDT while Kindle's highlight toolbar was visibly active. The persisted files were:

```text
files/kindle-accessibility-tree.txt    44,117 bytes
files/kindle-accessibility-events.txt 15,082 bytes
```

The tree proves that Kindle was in selection/highlight mode because it exposed these accessibility controls:

- `Dismiss selection`
- `Delete Highlight`
- `Highlight`
- `Look Up`
- `Note`
- `Pin`
- `Copy`

Despite the active highlight UI, Kindle did not expose the selected substring through standard Android accessibility semantics:

- Every inspected node had `isSelected() == false`.
- Every inspected node had text selection offsets `-1..-1`.
- No selected range appeared as a span in node text.
- No `TYPE_VIEW_TEXT_SELECTION_CHANGED` event was emitted.
- Recorded events were only window-state and window-content changes with no selection indices or selected text.
- The prose nodes remained full paragraph/page fragments rather than a selected fragment.

Conclusion: direct highlighted-text extraction through `AccessibilityNodeInfo.getTextSelectionStart()` and `getTextSelectionEnd()` does not work in the tested Kindle 8.148.1.0 highlight flow. The app's current `No highlighted text was exposed by Kindle` result is accurate.

## Why Context Is Too Large

The diagnostic tree explains why the current capture includes substantial text before and after the visible page. Kindle keeps neighboring pages in its virtual accessibility hierarchy.

Examples from the highlighted-state dump:

- Previous-page prose had off-screen bounds such as `Rect(-715, 70 - -109, 587)`.
- The visible-page prose had bounds such as `Rect(109, 70 - 715, 1527)`.
- Following-page prose had off-screen bounds such as `Rect(933, 70 - 1539, 681)` and `Rect(1757, 297 - 2363, 1519)`.
- The physical display width was 824 pixels.

The current collector ignores bounds and joins text from every prose node. A practical next improvement is to retain only prose nodes whose bounds intersect the physical display. This should isolate the visible page even when Kindle does not expose the exact highlight.

## Next Experiments

### 1. Invoke Kindle Copy

The active toolbar exposes a clickable accessibility node with content description `Copy`. On K press, the service can attempt to find that node and call `performAction(AccessibilityNodeInfo.ACTION_CLICK)` before opening the POC. It can then try to read the copied text from Android's clipboard.

This may provide the exact highlighted substring even though Kindle omits selection offsets. It needs a focused experiment because Android clipboard access rules, timing, and Kindle behavior may affect whether an accessibility service can read the result. Triggering Copy will also dismiss or alter Kindle's selection UI, so it must remain an explicit user-triggered action.

### 2. Filter Context By Screen Bounds

Change prose collection to ignore nodes completely outside the display bounds. This is independent of clipboard success and should reduce the AI context from multiple virtual pages to the currently visible page.

### 3. Remove Or Gate Diagnostics

The current diagnostic build writes complete tree and event details into app-private files for investigation. This includes book prose. Before treating the POC as production-like, remove the diagnostics or guard them behind a development-only option, and avoid retaining unbounded event history.

## Recommended Capture Flow

The best current design direction is:

```text
user highlights Kindle text
  -> user presses K
  -> service tries Kindle's exposed Copy action
  -> if clipboard text is available, use it as the primary AI input
  -> collect only on-screen prose nodes as surrounding context
  -> switch to the POC app
  -> clearly show highlighted text found/not found and visible-page context
```

If Copy cannot be used, the fallback remains the visible-page accessibility prose filtered by screen bounds. Screenshots remain available as a later fallback for unsupported formats, images, or layouts, but are not currently part of the text-only UI.
