# Personal Fitness Data Explorer — V0 Plan

## Goal

Build a local-first Garmin workout data system with a clean separation between:

1. **Raw Garmin sync** — download and cache original workout files locally with minimal transformation.
2. **Re-runnable data pipeline** — parse those raw files into DuckDB for querying and UI use.
3. **Simple V0 browser** — show workouts in a dense table with basic stats and a static route thumbnail.

The important V0 asset is the **local raw archive**. DuckDB and the schema can evolve freely because the database can always be rebuilt from the cached source files.

---

## Stack

- **Runtime / package manager:** Bun
- **Language:** TypeScript
- **Full-stack framework:** TanStack Start
- **Frontend:** React
- **Build:** Vite
- **Backend/domain logic:** Effect
- **Validation:** Effect Schema
- **Database:** DuckDB
- **FIT parsing:** Garmin FIT SDK / compatible parser
- **Garmin acquisition:** unofficial Garmin Connect client or CLI
- **Route thumbnail:** static SVG generated from GPS points

No separate REST API or tRPC layer is needed initially. TanStack Start server functions can provide the typed client/server boundary.

---

# Architecture

```text
Garmin Connect
      │
      │ garmin:sync
      ▼
local raw mirror
(data/raw/garmin/...)
      │
      │ build/import pipeline
      ▼
   DuckDB
      │
      ▼
TanStack Start
      │
      ▼

```

The raw mirror and the DuckDB pipeline are intentionally separate.

# 1. Garmin Raw Mirror

`garmin:sync` should mean one thing:

> Make the local Garmin workout archive match the workouts available in Garmin Connect.

It should perform as little transformation as possible.

## First sync

```text
list all Garmin activities
        ↓
for each activity
        ↓
download original/raw activity file
        ↓
save locally
```

Suggested layout:

```text
data/
  raw/
    garmin/
      manifest.json
      activities/
        <garmin-activity-id>.fit
        <garmin-activity-id>.fit
        ...
```

If Garmin returns a ZIP or another original representation for a particular activity, preserve what Garmin returned rather than normalizing it during sync.

## Subsequent syncs

```text
query Garmin activity list
        ↓
activity already cached?
   yes → skip
   no  → download original file
```

The sync should be **idempotent**.

Running it repeatedly should never duplicate data or rewrite raw files unnecessarily.

A later optimization can stop pagination once enough already-known activities are encountered, but V0 does not need to be clever.

## Manifest

Keep the manifest minimal. For example:

```json
{
  "18439201832": {
    "filename": "activities/18439201832.fit",
    "downloadedAt": "2026-08-19T20:30:00Z",
    "sha256": "..."
  }
}
```

Useful fields:

- Garmin activity ID
- local filename/path
- downloaded timestamp
- file hash

Do not put parsed workout data in this manifest.

## Authentication

Use an existing unofficial Garmin Connect client rather than implementing Garmin's private API.

Authentication/session state should be cached outside the project data directory, for example:

```text
~/.config/fitness/garmin/
```

Do not store Garmin credentials or auth tokens in DuckDB.

Suggested commands:

```bash
bun run garmin:login
bun run garmin:sync
```

The Bun command can invoke a tiny Python or CLI adapter if the maintained Garmin client ecosystem is better there.

The Garmin-specific code should be treated as a replaceable ingestion adapter.

# 2. Re-runnable Data Pipeline

Completely separate from Garmin sync:

```text
data/raw/garmin/*
        │
        │ parse / transform
        ▼
  fitness.duckdb
```

Suggested command:

```bash
bun run build:data
```

or simply:

```bash
bun run build
```

The important property is that this pipeline is **fully reproducible from local raw files**.

If the schema or parser changes:

```bash
rm data/fitness.duckdb
bun run build:data
```

No Garmin access should be required.

This is where parsing, normalization, unit conversion, derived fields, and later analytical transforms belong.

Not in `garmin:sync`.

---

# 3. DuckDB

Use one local database initially:

```text
data/fitness.duckdb
```

Do not over-design the schema yet.

V0 only needs enough structure to support the workout table and preserve useful high-resolution workout samples.

A minimal starting point is probably:

```text
activities
activity_samples
```

## `activities`

Enough fields for the table:

```text
id
source
source_activity_id
sport
started_at
duration_seconds
distance_m
ascent_m
avg_hr_bpm
max_hr_bpm
```

Add fields when the UI or analysis actually needs them.

## `activity_samples`

Preserve the important time-aligned signals available in FIT:

```text
activity_id
timestamp
lat
lon
distance_m
altitude_m
speed_mps
heart_rate_bpm
cadence
power_w
```

This is intentionally not a final schema.

The raw FIT file remains the authoritative source if fields need to be reinterpreted later.

## Database abstraction

Put DuckDB behind a small `Database` service so the rest of the app is not coupled to a particular JS binding.

Try the official Node DuckDB binding under Bun first. If native compatibility is flaky, the implementation can temporarily use the DuckDB CLI/subprocess without changing domain code.

Do not spend much time abstracting beyond that.

# 6. Route Thumbnail

The mini map does **not** need to be interactive in V0.

Do not instantiate a full map renderer for every table row.

Instead:

```text
GPS points
   ↓
project to local 2D coordinates
   ↓
normalize to thumbnail bounds
   ↓
SVG polyline/path
```

Example:

```text
┌──────────────┐
│    ╭─────╮   │
│ ╭──╯     ╰╮  │
│─╯         ╰──│
└──────────────┘
```

Requirements:

- static
- cheap to render
- preserve route shape
- no controls
- no zoom/pan
- no external map tiles required

Later, clicking a workout can open a detail page with a real interactive map if useful.

That is not part of V0.

# 7. Commands

Target developer workflow:

```bash
# authenticate once / when needed
bun run garmin:login

# Garmin → local raw archive
bun run garmin:sync

# local raw archive → DuckDB
bun run build:data

# run application
bun run dev
```

The important semantic distinction is:

```text
garmin:sync = acquire/cache source data
build:data   = parse/transform/index source data
```

Never combine those responsibilities.

# 9. V0 Milestones

## Milestone 0 — Runtime spike

Get this working:

```text
TanStack Start
+ React
+ Bun
+ Effect
+ DuckDB
```

Prove:

```text
browser
  ↓
TanStack server function
  ↓
DuckDB query
  ↓
React render
```

Do not build anything else until DuckDB works reliably under the chosen Bun integration.

---

## Milestone 1 — Garmin raw mirror

Implement:

```bash
bun run garmin:login
bun run garmin:sync
```

First sync downloads all available workout originals.

Later syncs download only missing workouts.

**Done when:** local raw workout files can be deleted from Garmin's equation entirely for all downstream work.

---

## Milestone 2 — Raw FIT → DuckDB

Parse locally cached activity files.

Populate minimal `activities` and `activity_samples` tables.

Pipeline is fully rerunnable.

**Done when:** deleting DuckDB and rebuilding produces the same useful local dataset without contacting Garmin.

---

## Milestone 3 — Workout table

Render latest workouts from DuckDB.

Show basic metadata only.

**Done when:** the app is already a useful replacement for browsing Garmin workout history at a glance.

---

## Milestone 4 — Static route thumbnails

Generate simple SVG route previews from GPS samples.

**Done when:** runs/rides can be visually distinguished by route without any interactive map infrastructure.

That completes V0.

# 11. Future Directions to Preserve

Do not implement these now, but avoid destroying the data needed for them.

## Cycling power estimation

Later derive power estimates from combinations of:

```text
speed
GPS
altitude / grade
acceleration
body mass
bike mass
rolling resistance
CdA
wind assumptions
```

Preserving high-resolution GPS, time, altitude, speed, cadence, and HR is enough for now.

## HR at equivalent workload

Future analysis examples:

```text
HR at ~200 W over time
cardiac drift at constant workload
HR response after workload transitions
speed vs HR on equivalent climbs
```

## Route/sub-route matching

A future analysis should be able to detect overlapping trajectory segments even when entire workouts differ.

Example:

```text
Workout A:  ─────────────────────────────
Workout B:          ───────────────────────────
Overlap:            ────────────────
```

This argues for preserving full-resolution timestamps + GPS samples in the raw archive and preferably in the imported sample table.

No route-matching implementation belongs in V0.

---

# Core Principles

1. **Garmin sync only acquires raw data.**
2. **Raw files are immutable and locally cached.**
3. **DuckDB is disposable/rebuildable.**
4. **Transformations happen only in the local pipeline.**
5. **Schema evolves from actual analytical needs rather than being designed upfront.**
6. **Preserve high-resolution source data whenever practical.**
7. **Vendor-specific logic ends at ingestion.**
8. **V0 UI is just a workout table plus static route thumbnails.**
9. **Build the smallest useful vertical slice first.**
